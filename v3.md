# v3 Direction

## Goal
v3 should deepen trust and extensibility without changing the product into a broad scanner or platform.

Build on top of the current validated v2 codebase.

Keep the product narrow:
- Next.js + Supabase + Vercel
- beginner / student / hackathon / solo vibe-coder users
- heuristic static pre-deploy checker
- ship / caution / no output remains

## Why this v3
The current v2 is good enough to serve as a base for v3, but still has known heuristic limits and needs better trust, tuning, and internal structure before broader packaging or platform expansion.

v3 should focus on:
1. better rule quality
2. cleaner rule-pack registration
3. more trustworthy stack/profile scoring
4. tuning against more realistic target-stack repos
5. preserving a narrow and honest product shape

## v3 scope

### In scope
- refine the current nextjs-supabase-vercel profile using real or realistic sample repos
- improve score thresholds and confidence handling where needed
- improve wording and evidence clarity for beginner users
- introduce a cleaner rule-pack registration structure
- keep support for one active profile in behavior, but make the codebase cleaner for future profiles
- improve report trustworthiness
- keep CLI-first architecture

### Out of scope
- GitHub Action packaging
- multiple fully supported stack profiles
- dashboard
- SaaS backend
- auth/accounts/billing/team features
- dynamic/runtime validation
- deep semantic analysis
- broad generic SAST direction
- enterprise policy features

## Product principles
- narrow scope beats broad expansion
- trust and clarity matter more than feature count
- avoid false confidence
- findings must stay fix-first and beginner-readable
- no over-engineering
- no rewrite

## Desired v3 outcomes
- stronger trust in current findings and scoring
- cleaner internal rule-pack structure
- better tuning on realistic repos
- a clearer base for a later v4 or v3.5 that could add GitHub Action packaging

## Success criteria
v3 is successful if:
- the scanner remains coherent and narrow
- scoring and wording are more trustworthy
- rule-pack structure is cleaner
- real-sample tuning improves confidence
- the codebase is better prepared for future profiles without pretending to support them yet

You are helping build v1 of a developer security tool.

Build a CLI-first MVP for this product:

Product:
A pre-deploy security checker for vibe-coded apps, focused on the stack:
- Next.js
- Supabase
- Vercel

Primary users:
- students
- hackathon teams
- solo vibe-coders

Main purpose:
Before deployment, scan a local repo and detect common high-risk mistakes in:
1. Supabase RLS / auth usage
2. public env / secrets / config exposure

This is NOT a generic security scanner.
This is a narrow, opinionated, beginner-friendly preflight checker for one stack.

Main v1 output:
- terminal summary
- markdown report
- JSON report
- final recommendation:
  - ship: no
  - ship: caution
  - ship: yes

Main v1 goals:
1. detect stack presence
2. run a small set of practical rules
3. produce useful fix-first reports
4. keep the codebase clean and extensible for future stack profiles

Important product positioning:
Do not build a broad SAST platform.
Do not add web dashboard, login, billing, teams, SaaS backend, or enterprise features.
Do not try to support multiple frameworks in v1.
Do not pretend the tool guarantees security.
Do not generate noisy low-value warnings.

What to build in v1

A. CLI
Create a CLI command such as:
- preflight scan
or similar

The CLI should:
- scan the current repo or a provided path
- detect whether the project appears to use Next.js + Supabase + Vercel
- run rule checks
- print a summary
- write a markdown report
- write a JSON report
- exit with a useful status code if possible

B. Stack detection
Detect likely use of:
- Next.js
- Supabase
- Vercel

Use practical heuristics like:
- package.json dependencies
- presence of next.config.* or app/ or pages/
- presence of supabase/ folder, Supabase client code, env variable names
- presence of vercel.json or Vercel-specific configuration patterns

If stack confidence is weak, say so clearly in output.

C. Rules for v1
Implement a SMALL, useful ruleset only.
Focus on high-value checks.

Category 1: Supabase RLS / auth mistakes
Examples of checks:
- possible service role key exposure in client-side code
- suspicious use of Supabase keys in browser-reachable code
- signs that Supabase is used but RLS assumptions may be weak or missing
- auth-related routes / handlers / middleware patterns that suggest incomplete protection
- server actions / API routes that look sensitive but may lack auth checks

Category 2: public env / secrets / config exposure
Examples of checks:
- suspicious use of NEXT_PUBLIC_ with sensitive-looking variable names
- hardcoded secrets or tokens
- dangerous env variable naming or placement
- likely accidental client exposure of privileged values
- obvious secrets committed in files that should not contain them
- configuration patterns that may expose sensitive behavior or widen access unnecessarily

Important:
Do not overclaim.
Some findings should be phrased as:
- confirmed issue
- likely issue
- review needed
Make confidence levels explicit.

D. Severity model
Use a simple severity system:
- Blocker
- High
- Medium

Use severity plus confidence to decide final ship status.

Suggested logic:
- any confirmed Blocker => ship: no
- multiple High findings => ship: caution or no
- only Medium / review-needed findings => ship: caution
- clean scan with no major findings => ship: yes

E. Reporting
For each finding include:
- rule id
- title
- severity
- confidence
- category
- file path
- short explanation
- why this matters
- suggested minimum fix

Report style:
- concise
- beginner-readable
- practical
- not academic

Markdown report should include:
1. project summary
2. detected stack
3. findings by severity
4. final ship recommendation
5. limitations / what was not checked

JSON report should be machine-readable and future GitHub Action friendly.

F. Architecture
Design code so it can grow later into:
- more stack profiles
- more rule packs
- GitHub Action support
- optional SaaS wrapper

Suggested structure:
- CLI entrypoint
- project / stack detection module
- rule engine
- rule definitions
- reporter module
- shared types / models

Prefer maintainable and simple code over over-engineered abstractions.

G. Tech decisions
Choose a sensible language and structure for a CLI MVP.
Prefer one of:
- TypeScript / Node.js
- Python

Default preference:
TypeScript / Node.js
Reason:
- natural fit for Next.js ecosystem
- easier future GitHub Action integration

L. Success criteria for v1
v1 is successful if:
- it can scan a local repo
- detect the target stack with reasonable confidence
- catch a meaningful subset of common stack-specific mistakes
- output a useful beginner-friendly report
- feel like a real deploy gate rather than a generic scanner clone

Start by:
1. summarizing scope
2. proposing architecture
3. listing the exact first v1 rules
4. then implementing step by step

Exact v1 boundary:
For v1, do NOT try to deeply analyze all authentication logic or fully validate all Supabase policies.
Keep checks practical and heuristic-based.

For v1, focus only on these concrete checks:

1. Supabase / auth related
- detect likely exposure of Supabase service_role keys
- detect suspicious Supabase key usage in client-reachable code
- detect likely missing auth checks in obviously sensitive API routes or server actions
- detect likely weak or missing RLS signals based on project structure, migrations, or Supabase-related files
- mark uncertain findings as review-needed instead of overclaiming

2. Env / secrets / config related
- detect hardcoded secrets or tokens
- detect suspicious NEXT_PUBLIC_ usage with sensitive-looking names
- detect likely accidental exposure of privileged env values to client-side code
- detect dangerous env/config patterns that widen access unnecessarily

Important:
This tool is a preflight checker, not a full security verifier.
It should prefer a small number of high-value findings over many noisy findings.

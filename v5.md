# v5 Direction

## Goal
v5 should validate the packaged scanner in real usage conditions and prepare the repo for basic public/open-source release.

Build directly on top of the accepted v4 codebase.

Keep the current product shape:
- CLI-first core
- GitHub Action support
- Next.js + Supabase + Vercel focused
- beginner-friendly
- heuristic static pre-deploy checker
- ship / caution / no recommendation remains
- one active profile in actual behavior

## Why v5
v4 packaged the scanner for GitHub Action / CI usage.
The next step is not broader feature expansion.

The next step is:
1. real hosted GitHub Actions validation
2. more representative public-repo validation
3. clearer release-ready documentation
4. honest open-source positioning

v5 is a validation and release-readiness phase.

## v5 scope

### In scope
- validate the Action in real hosted GitHub Actions runs
- validate the scanner against a small set of representative public target-stack repos
- record validation results clearly
- identify obvious false positives and false negatives
- make only narrow fixes required by validation
- improve README and docs for honest public/open-source usage
- clarify product boundaries, limitations, and intended usage
- prepare the repo for a basic public/open-source release
- optionally prepare a lightweight release checklist or release notes draft

### Out of scope
- no major feature expansion
- no multiple user-facing profiles
- no new framework support
- no SaaS backend
- no dashboard
- no billing, accounts, or teams
- no deep semantic analysis rewrite
- no runtime verification
- no broad SAST positioning
- no enterprise policy engine

## Product principles
- validation before expansion
- trust over feature count
- no false confidence
- narrow scope stays narrow
- fix only what real validation shows is needed
- docs must match real behavior

## Desired v5 outcomes
- the GitHub Action is validated in real hosted usage
- validation results on representative repos are documented
- obvious trust issues found during validation are fixed
- README clearly explains what the tool is and is not
- the repo is credible as a small public/open-source CLI + Action project

## Success criteria
v5 is successful if:
- the Action has been exercised in a real hosted GitHub Actions run
- a small representative validation set has been tested
- validation findings are summarized clearly
- only necessary fixes were made
- the docs are honest and public-ready
- the project is ready for a basic public/open-source release without overstating security guarantees

## Validation expectations
Validate at least:
- hosted GitHub Actions execution on this repo or a small test repo
- clean strong-match case
- unsafe case
- caution case
- several representative real public repos that resemble the target stack
- JSON and Markdown outputs remain useful in practice

## Notes
This version should not become a broad new development phase.
If new ideas appear, defer them unless they are required to complete validation or basic release readiness.

# v4 Direction

## Goal
v4 should package the current scanner for practical GitHub Action / CI usage without changing the product into a broader platform.

Build directly on top of the accepted v3 codebase.

Keep the current product shape:
- CLI-first core
- Next.js + Supabase + Vercel focused
- beginner-friendly
- heuristic static pre-deploy checker
- ship / caution / no recommendation remains
- one active profile in actual product behavior

## Why v4
v3 improved trust, wording, tuning, and internal structure.
The next natural step is packaging the existing scanner for repeatable CI usage.

v4 is not a scope-expansion phase.
It is a packaging and integration phase.

## v4 scope

### In scope
- package the scanner for GitHub Action / CI usage
- preserve the existing CLI behavior as much as possible
- define a clean Action interface for scanning a repo in CI
- make JSON output reliable for automation use
- keep Markdown output useful for human review
- document CI usage clearly
- make result handling predictable through exit codes
- improve small integration details only where needed for packaging
- add a minimal example workflow for GitHub Actions
- keep trust language explicit so CI users do not overread `ship: yes`

### Out of scope
- no SaaS backend
- no web dashboard
- no billing, accounts, or team features
- no multiple user-facing profiles
- no major rule expansion
- no deep semantic analysis rewrite
- no runtime verification
- no enterprise policy engine
- no broad generic SAST positioning

## Product principles
- packaging over expansion
- preserve trust boundaries
- no false confidence
- keep the scanner narrow and understandable
- do not break the current CLI unless necessary
- prefer simple CI ergonomics over feature growth

## Desired v4 outcomes
- the scanner can run cleanly inside GitHub Actions
- outputs are useful both for machines and humans
- exit-code behavior is documented and intentional
- the repo is easier to adopt as an open-source CLI + Action
- trust language remains honest in CI contexts

## Success criteria
v4 is successful if:
- a GitHub Action workflow can run the scanner on a repo
- JSON output is stable enough for downstream automation
- Markdown output still works as a readable report
- exit codes are clearly documented for CI use
- the Action setup is simple and narrow
- the product still does not pretend to prove safety

## Validation expectations
Validate at least:
- local CLI still works as before
- Action example workflow runs successfully
- clean strong-match fixture still behaves as expected
- unsafe fixture still fails as expected
- caution case still behaves as expected
- generated outputs are usable in CI logs or artifacts

## Notes
This version should prepare the codebase for practical CI adoption, not broader market expansion.
If additional scope appears during implementation, default to not building it unless it is required for packaging.
